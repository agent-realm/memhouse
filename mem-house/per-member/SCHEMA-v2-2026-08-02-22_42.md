# SCHEMA — rooms per member — v2 (2026-08-02-22_42)

Supersedes `SCHEMA.md` (v1). House is now `mem`; room names lead with the room type.

## Naming

```
mem.sessions_<member>
mem.messages_<member>
mem.tool_calls_<member>

mem.all_sessions            -- Merge, owner-managed
mem.all_messages
mem.all_tool_calls
```

`<member>` is the ClickHouse username, unmodified.

**The Merge regex is now safe by construction:**

```sql
Merge('mem', '^sessions_')      -- matches sessions_alice, never all_sessions
Merge('mem', '^messages_')
Merge('mem', '^tool_calls_')
```

v1's `^.*_messages$` matched `all_messages` itself. Anchoring on the room type removes
the whole class.

> **OPEN:** forbid `_` in handles anyway? `messages_alice_bob` is ambiguous to a reader
> and to any future name-splitter, even though nothing security-critical now parses it.

## Room shapes

Unchanged from `../schema.sql` apart from the name. Each room keeps its typed columns,
`extra JSON`, `ingested_at`, and `ENGINE = ReplacingMergeTree(ingested_at)`.

`messages_<member>` keeps both full-text layers — `text_ngram` (`ngrams(3)`, for
substring and `LIKE`) and `text_word` (`splitByNonAlpha`, for whole-word), each carrying
one text index.

### `user_id` is retained

The room already names the member, so the column looks redundant. Keep it:

- a room shared with a colleague still says who wrote each row;
- the Merge rooms stay meaningful — `_table` says which room, `user_id` says who wrote
  it, and the two can disagree once rooms are shared;
- it is the only column a client cannot forge, since it is stamped
  `MATERIALIZED currentUser()` server-side.

That last point is now sharper than in v1: **ClickHouse has no impersonation.**
`SET SESSION AUTHORIZATION` does not exist and `SET ROLE` does not change
`currentUser()` (both tested). So a row stamped `alice` was written by alice's
credential, with no exceptions to reason about.

Requires `async_insert=0` on writers, as today.

## Sort keys

Today's shared rooms use `(session_id, user_id, seq)`. With one room per member the
`user_id` slot no longer discriminates.

> **OPEN:** drop to `(session_id, seq)`, or keep `user_id` for rooms that end up holding
> more than one writer? That only happens if a member writes into a room they were
> granted — not a supported flow today, and worth deciding whether it ever should be.

## The Merge rooms

Measured behaviour this design leans on:

- **Fails closed.** A caller granted the Merge room plus only their own underlying room
  sees only their own rows. So Merge rooms can be granted broadly rather than reserved
  for an analytics role.
- **Auto-discovers.** A room created after the Merge room existed was picked up with no
  redefinition — onboarding costs nothing on the read side.
- **Tolerates drift.** A room missing a column yields that column's default rather than
  failing the query.
- **Rejects mutations.** `ALTER … MATERIALIZE COLUMN` on a Merge room errors with
  `Table engine Merge doesn't support mutations`. Merge rooms are read paths only; add
  columns with `ADD COLUMN`.

> **OPEN:** is `all_sessions` a Merge over the member `sessions_*` rooms, or a saved
> query over `all_messages`? The first is cheaper; the second guarantees the aggregates
> match the per-member view exactly.

## `sessions_v` is a saved query, not a room

Substituted with the caller's room names and run under the caller's own credential, so
it inherits their grants and raises no view-ownership question.

Two properties of the current view must survive the port: the join is a **LEFT JOIN**,
so a session with no messages still appears with zero aggregates instead of vanishing;
and `join_use_nulls = 1` makes unmatched columns NULL so the `coalesce` calls produce
true zeros rather than counting a placeholder row.

The aggregate shape is otherwise unchanged — see `../schema.sql`.
