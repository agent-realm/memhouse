# SCHEMA — rooms per member — v3 (2026-08-02-22_49)

Supersedes `SCHEMA-v2-2026-08-02-22_42.md`. Only the `user_id` trust claim changes; the
layout is identical to v2.

## Naming

```
mem.sessions_<member>
mem.messages_<member>
mem.tool_calls_<member>

mem.all_sessions            -- Merge, owner-managed
mem.all_messages
mem.all_tool_calls
```

Merge rooms anchor on the room type, so they cannot match themselves:

```sql
Merge('mem', '^sessions_')      -- matches sessions_alice, never all_sessions
Merge('mem', '^messages_')
Merge('mem', '^tool_calls_')
```

> **OPEN:** forbid `_` in handles anyway? `messages_alice_bob` is ambiguous to a reader
> and to any future name-splitter, though nothing security-critical parses it now.

## Room shapes

Unchanged from `../schema.sql` apart from the name: typed columns, `extra JSON`,
`ingested_at`, `ENGINE = ReplacingMergeTree(ingested_at)`.

`messages_<member>` keeps both full-text layers — `text_ngram` (`ngrams(3)`, substring
and `LIKE`) and `text_word` (`splitByNonAlpha`, whole-word), each with one text index.

### `user_id` is retained — and what it actually guarantees

Keep the column even though the room names the member:

- a room shared with a colleague still says who wrote each row;
- the Merge rooms stay meaningful — `_table` says which room, `user_id` says who wrote
  it, and the two can disagree once rooms are shared.

**Corrected from v2.** v2 claimed the stamp was "proof rather than convention" on the
grounds that ClickHouse has no impersonation. That was wrong — `EXECUTE AS` exists and
changes `currentUser()` (measured on 26.7.1). The accurate statement is narrower:

> `user_id` is **unforgeable by a member**, because `EXECUTE AS` is a grantable privilege
> that members do not hold — a plain member attempting it gets `Not enough privileges`.
> It is forgeable by anyone granted `EXECUTE AS`, including the owner.

So the trust boundary is the owner, not the engine. That is the normal arrangement — the
owner is already trusted with everything in its own house — but it must not be
overstated in anything user-facing. **Do not grant `EXECUTE AS` to members.**

Writers still need `async_insert=0` for the stamp to work.

## Sort keys

Today's shared rooms use `(session_id, user_id, seq)`. With one room per member the
`user_id` slot no longer discriminates.

> **OPEN:** drop to `(session_id, seq)`, or keep `user_id` for rooms that could hold more
> than one writer? That only arises if a member writes into a room they were granted —
> not a supported flow today.

## The Merge rooms

Measured behaviour this leans on:

- **Fails closed.** A caller granted the Merge room plus only their own underlying room
  sees only their own rows — so Merge rooms can be granted broadly.
- **Auto-discovers** rooms created after the Merge room existed.
- **Tolerates drift** — a room missing a column yields that column's default.
- **Rejects mutations** — `ALTER … MATERIALIZE COLUMN` errors with
  `Table engine Merge doesn't support mutations`. Read paths only; add columns with
  `ADD COLUMN`, Merge room first.

> **OPEN:** is `all_sessions` a Merge over the member `sessions_*` rooms, or a saved query
> over `all_messages`? The first is cheaper; the second guarantees the aggregates match
> the per-member view exactly.

## `sessions_v` is a saved query, not a room

Substituted with the caller's room names and run under the caller's credential, so it
inherits their grants and raises no view-ownership question.

Two properties of the current view must survive the port: the join is a **LEFT JOIN**, so
a session with no messages still appears with zero aggregates instead of vanishing; and
`join_use_nulls = 1` makes unmatched columns NULL so `coalesce` produces true zeros
rather than counting a placeholder row.
