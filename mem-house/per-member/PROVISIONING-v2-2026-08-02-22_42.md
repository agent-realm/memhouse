# PROVISIONING — minting a member and their rooms — v2 (2026-08-02-22_42)

Supersedes `PROVISIONING.md` (v1). House is `mem`; rooms lead with the room type.

## The grant set

Three explicit grants per member — one per room. **No wildcards, in either direction.**

```sql
GRANT SELECT, INSERT ON mem.sessions_<m>   TO <m> WITH GRANT OPTION;
GRANT SELECT, INSERT ON mem.messages_<m>   TO <m> WITH GRANT OPTION;
GRANT SELECT, INSERT ON mem.tool_calls_<m> TO <m> WITH GRANT OPTION;
```

Why not wildcards, restated because it is the one measured trap that would silently
leak memory: `GRANT … ON mem.alice_*` also matches `alice_bob_*`, so a member whose
handle prefixes another's reads their rooms. Suffix wildcards (`mem.*_alice`) are a
syntax error, so they were never an option. Explicit grants are cheap — the kernel runs
multi-statement SQL, and three statements is not a burden.

`WITH GRANT OPTION` is what makes whole-room sharing self-serve (`SHARING-v2`). Without
it every share becomes an operator ticket, which is most of the reason this fork exists.

The owner (`mem_root`) holds `ALL ON mem.* WITH GRANT OPTION`, so a second member
joining an existing house needs no new owner setup — house, owner, and Merge rooms are
already there.

> **OPEN:** does the member also get `CREATE TABLE` / `DROP TABLE` on their own rooms?
> The lab confirms a member so granted creates their rooms and is **denied outside their
> prefix**, which would let `--ensure-schema` run as the member and make onboarding need
> no owner involvement at all. Against: the member can then drop their own memory, and
> schema rollout stops being centrally enforceable.

## Kernel path

Capabilities run multi-statement branching SQL, so provisioning is one capability rather
than a runbook.

```
install-agency{mem}             -- once: house + mem_root + owner grants + Merge rooms
register-member{handle}         -- ego mints the identity, mayor approves
provision-member-rooms{handle}  -- NEW: 3 rooms + 3 grants, idempotent
```

`provision-member-rooms` should:

1. validate the handle,
2. `CREATE TABLE IF NOT EXISTS` the three rooms from the DDL template,
3. issue the three grants,
4. be safe to re-run — it is also the hook for rolling a schema change across rooms.

Nothing needs to touch the Merge rooms on member join: they are a regex over names and
**auto-discover** rooms created after them (measured).

> **OPEN:** does this capability run as the ego or as `mem_root`? The owner holds the
> rights; the ego owns the approval flow. Probably owner, invoked by the ego.

## Standalone path

No kernel, so no capability layer; the CLI performs the same three steps.

> **OPEN:** a standalone user is simultaneously owner and member. One credential holding
> both roles, or two? Today's `memhouse install` assumes a single credential that owns
> everything, which no longer maps cleanly.

## Row-policy rights

`GRANT ACCESS MANAGEMENT ON mem.*` expands to
`CREATE/ALTER/DROP/SHOW ROW POLICY ON mem.*` — house-scoped, no global access management
required. This is what lets the owner serve partial-share requests.

**Owner only.** The scope is the house, not a room prefix, so any holder could attach a
policy to another member's rooms. Policies filter rather than grant, so it is not a data
leak — but it is a denial of service on a colleague's own reads.
