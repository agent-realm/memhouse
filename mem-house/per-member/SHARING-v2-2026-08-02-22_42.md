# SHARING — two tiers — v2 (2026-08-02-22_42)

Supersedes `SHARING.md` (v1). House is `mem`; rooms lead with the room type.

## Tier 1 — whole room, self-serve

A member holds `WITH GRANT OPTION` on their own rooms, so they share without an
operator:

```sql
GRANT SELECT ON mem.messages_alice   TO bob;
GRANT SELECT ON mem.sessions_alice   TO bob;
GRANT SELECT ON mem.tool_calls_alice TO bob;
```

This is the tier per-member rooms exist to enable. Under a row policy the same act needs
`CREATE ROW POLICY`, which members do not have and which the kernel withholds from
agency owners by default.

Bob reading `messages_alice` sees `user_id = 'alice'` on every row, because `user_id`
survives as a materialized column — and, since ClickHouse has no impersonation
(measured), that stamp is proof rather than convention.

Bob's own Merge-room reads now include alice's rooms automatically: `Merge` reduces to
the caller's actual grants, so a share widens what `all_messages` returns for bob and
nothing else changes.

> **OPEN:** a `share` / `unshare` CLI verb wrapping the three grants, so a member never
> types SQL. Mirrors memory-house's `mh-share`.

## Tier 2 — some rows, owner-mediated

Row policies remain the only way to share a *subset*. The member asks the owner, who
holds house-scoped policy rights:

```sql
GRANT SELECT ON mem.messages_alice TO bob;                -- privilege
CREATE ROW POLICY share_alice_to_bob ON mem.messages_alice
  FOR SELECT USING <predicate> TO bob;                    -- restriction
```

Both halves are required: a policy filters, it never grants. Privilege without a policy
shares everything; a policy without privilege shares nothing.

> **OPEN:** which predicates are worth supporting — by project, by date range, by
> `source`? Free-form SQL from a member is an injection surface, so this likely wants a
> small fixed vocabulary rather than arbitrary expressions.

## Why the tiers are asymmetric

Deliberate. Whole-room sharing is the common case, is coarse, and is safe to self-serve
— the worst outcome is oversharing your own data. Partial sharing writes a filter into
the house's access model, so it goes through the owner.

## What sharing does not do

**It is not a boundary between agents sharing one credential.** A crew running under a
single member credential reads and writes the same rooms; nothing here separates them,
and any per-agent tag is client-supplied. Enforced separation means separate ClickHouse
users, which means separate rooms — this design one level down. Deferred along with
`agent_id`.
