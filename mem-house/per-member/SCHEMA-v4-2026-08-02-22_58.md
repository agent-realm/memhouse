# SCHEMA — rooms per member — v4 (2026-08-02-22_58)

Supersedes `SCHEMA-v3-2026-08-02-22_49.md`. Only the stale handle-ambiguity note is
dropped; the layout is identical.

## Naming

```
mem.sessions_<member>
mem.messages_<member>
mem.tool_calls_<member>

mem.all_sessions            -- Merge, owner-managed
mem.all_messages
mem.all_tool_calls
```

The one wildcard in the design is the Merge regex, anchored on the room type:

```sql
Merge('mem', '^sessions_')
Merge('mem', '^messages_')
Merge('mem', '^tool_calls_')
```

Anchoring on a fixed room type means the pattern matches member rooms only and can never
match `all_sessions`. Handles need no restriction for this to hold.

## Room shapes

Unchanged from `../schema.sql` apart from the name: typed columns, `extra JSON`,
`ingested_at`, `ENGINE = ReplacingMergeTree(ingested_at)`.

`messages_<member>` keeps both full-text layers — `text_ngram` (`ngrams(3)`, substring and
`LIKE`) and `text_word` (`splitByNonAlpha`, whole-word), each with one text index.

### `user_id` is retained

Keep it even though the room names the member:

- a room shared with a colleague still says who wrote each row;
- the Merge rooms stay meaningful — `_table` says which room, `user_id` says who wrote it,
  and the two can disagree once rooms are shared.

**What it guarantees:** unforgeable **by a member**, since `EXECUTE AS` is a grantable
privilege members do not hold — a plain member attempting it gets `Not enough privileges`.
Forgeable by the owner or any grantee. The trust boundary is the owner, not the engine.
Do not grant `EXECUTE AS` to members, and do not overstate the guarantee anywhere
user-facing.

Writers need `async_insert=0` for the stamp to work.

## Sort keys

Today's shared rooms use `(session_id, user_id, seq)`. With one room per member the
`user_id` slot no longer discriminates.

> **OPEN:** drop to `(session_id, seq)`, or keep `user_id` for rooms that could hold more
> than one writer? That only arises if a member writes into a room they were granted — not
> a supported flow today.

## The Merge rooms

Measured behaviour this leans on:

- **Fails closed.** A caller granted the Merge room plus only their own underlying room
  sees only their own rows — so Merge rooms can be granted broadly rather than reserved
  for an analytics role.
- **Auto-discovers** rooms created after the Merge room existed, so member onboarding
  costs nothing on the read side.
- **Tolerates drift** — a room missing a column yields that column's default.
- **Rejects mutations** — `ALTER … MATERIALIZE COLUMN` errors with
  `Table engine Merge doesn't support mutations`. Read paths only; add columns with
  `ADD COLUMN`, Merge room first.

> **OPEN:** is `all_sessions` a Merge over the member `sessions_*` rooms, or a saved query
> over `all_messages`? The first is cheaper; the second guarantees the aggregates match
> the per-member view exactly.

## `sessions_v` is a saved query, not a room

Substituted with the caller's room names and run under the caller's credential, so it
inherits their grants and raises no view-ownership question.

Two properties of the current view must survive the port: the join is a **LEFT JOIN**, so
a session with no messages still appears with zero aggregates instead of vanishing; and
`join_use_nulls = 1` makes unmatched columns NULL so `coalesce` produces true zeros rather
than counting a placeholder row.
