# MIGRATION — deferred — v2 (2026-08-02-22_42)

Supersedes `MIGRATION.md` (v1), which planned a fan-out from the current shared-room
house. **Migration is a separate task and is not designed here.** This file exists only
so the two findings v1 uncovered are not lost.

## Why it is deferred

The new line uses a different house (`mem`, not `memhouse`) and a different room layout,
so it can be stood up beside the existing one rather than converted in place. A fresh
house needs no migration at all, and that is the path this fork optimises for.

## Finding 1 — there is no impersonation to migrate with

v1 assumed a fan-out could write each member's rows under that member's identity. Tested
on ClickHouse 26.7.1:

- `SET SESSION AUTHORIZATION` — does not exist (syntax error).
- `SET ROLE` — leaves `currentUser()` unchanged; roles carry privileges, not identity.

So a fan-out run by the owner would stamp `user_id = 'mem_root'` on every migrated row,
because `user_id` is `MATERIALIZED currentUser()` and cannot be inserted. The only way to
produce a row stamped `alice` is to authenticate as alice.

Whoever picks migration up will face the same three options v1 listed — run each
member's fan-out under their own credential, weaken `user_id` to a plain defaulted column
on the destination, or accept the rewrite and carry the original in `extra`. None is
free; the second gives up the unforgeable-provenance property the identity model rests
on.

## Finding 2 — schema rollout is progressive, not lock-step

This one applies to the new line too, and is genuinely good news for a house with many
rooms.

`Merge` returns a column's **default** for rooms that do not have it yet. So:

1. `ALTER` the Merge room first — it is the read path.
2. `ALTER` member rooms at any pace.

Reads never break mid-rollout; they show defaults until each room catches up. No
coordination window, no lock-step across N rooms.

Two traps, both measured:

- **`MATERIALIZE COLUMN` does not fix a Merge read.** The failure is a missing column on
  the *Merge room*, not missing values in the source.
- **`Merge` rejects mutations outright** — `ALTER … MATERIALIZE COLUMN` on a Merge room
  errors with `Table engine Merge doesn't support mutations`. Use `ADD COLUMN`, and do
  it on the Merge room first.

`provision-member-rooms` should own this: idempotent, re-runnable, responsible for both
member rooms and Merge rooms.
