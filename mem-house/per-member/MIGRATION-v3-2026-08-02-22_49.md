# MIGRATION — deferred, and no longer blocked — v3 (2026-08-02-22_49)

Supersedes `MIGRATION-v2-2026-08-02-22_42.md`, whose central claim was wrong.

**Migration is still a separate task and must not shape MVP decisions.** This file exists
so the findings are not re-derived, not so migration can be argued about now.

## Correction: `EXECUTE AS` exists, so provenance is not a blocker

v1 and v2 treated per-member provenance as the hard problem in any fan-out. `user_id` is
`MATERIALIZED currentUser()` and cannot be inserted, so a fan-out run by the owner would
stamp every migrated row `mem_root`. v2 went further and asserted ClickHouse has no
impersonation at all — wrong, from two negative tests (`SET SESSION AUTHORIZATION`,
`SET ROLE`) rather than a search for the feature that exists.

`EXECUTE AS` changes `currentUser()` (measured, 26.7.1):

```sql
EXECUTE AS alice INSERT INTO mem.messages_alice
SELECT … FROM memhouse.messages FINAL WHERE user_id = 'alice';
```

Rows land stamped `alice`, written by the owner, without holding alice's credential. The
blocker is gone.

It is a **grantable privilege denied by default** — a plain member gets
`Not enough privileges`; the owner or a grantee can use it. So migration needs the owner
to hold `EXECUTE AS`, and members must not.

> **OPEN:** is `EXECUTE AS` scopeable to a house (`ON mem.*`) rather than `ON *.*`? It was
> granted globally in the lab. Worth testing before any migration work, since a
> house-scoped grant would let an owner impersonate only its own members.

## Still true: schema rollout is progressive

Applies to the new line too, and is the useful property for a house with many rooms.
`Merge` returns a column's **default** for rooms that lack it, so:

1. `ALTER` the Merge room first — it is the read path.
2. `ALTER` member rooms at any pace.

Reads never break mid-rollout. No coordination window, no lock-step across N rooms.

Two traps, both measured:

- **`MATERIALIZE COLUMN` does not fix a Merge read** — the missing column is on the
  *Merge room*, not the source.
- **`Merge` rejects mutations** — `ALTER … MATERIALIZE COLUMN` errors with
  `Table engine Merge doesn't support mutations`. Use `ADD COLUMN`, Merge room first.

`provision-member-rooms` should own this: idempotent, re-runnable, responsible for member
rooms and Merge rooms alike.

## Still not in scope

- rollback, and whether the old `memhouse` house is retired, frozen, or left running
- `FINAL` on the source reads (needed — the shared rooms are `ReplacingMergeTree`, and
