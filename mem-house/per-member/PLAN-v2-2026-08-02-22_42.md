# per-member rooms — plan v2 (2026-08-02-22_42)

Supersedes `PLAN.md` (v1). v1 is kept as written; this file carries the decisions taken
since.

## Changes from v1

| | v1 | v2 |
|---|---|---|
| house | `memhouse` | **`mem`** — shorter, and signals a deliberately incompatible line |
| room naming | `<member>_messages` | **`messages_<member>`** — room type leads |
| Merge regex | `^.*_messages$` (matched itself) | **`^messages_`** — anchored, cannot match `all_messages` |
| migration | a phase | **deferred** — separate task, not designed here |

## The model

One house, `mem`. Each member gets three rooms:

```
mem.sessions_<member>
mem.messages_<member>
mem.tool_calls_<member>
```

Plus owner-managed Merge rooms for team-wide reads: `mem.all_sessions`,
`mem.all_messages`, `mem.all_tool_calls`.

Canon (`../../TERMINOLOGY.md`): *house* = database, *room* = table, *member* = a
registered user with grants.

## Why suffix naming settles two things at once

**The Merge self-match is gone.** `Merge('mem', '^messages_')` matches
`messages_alice`, `messages_bob`, and can never match `all_messages`. Under v1's
`^.*_messages$` the Merge room matched itself — a real bug waiting to happen.

**Room type leads, so pattern-matching is by kind, not by person.** Every tool that
wants "all message rooms" anchors on a fixed prefix rather than an unbounded one.

The cost v1 worried about — that suffix form cannot use wildcard grants
(`GRANT … ON mem.*_alice` is a syntax error) — is not a cost, because wildcard grants
are ruled out anyway: `GRANT … ON mem.alice_*` also matches `alice_bob_*`, silently
handing one member another's memory whenever a handle prefixes another handle.
**Three explicit grants per member. No wildcards, either direction.**

## What stays from v1

- `user_id String MATERIALIZED currentUser()` on every room — provenance survives a
  share, and keeps the Merge rooms meaningful. Do not drop it.
- Typed columns, `extra JSON`, `ReplacingMergeTree(ingested_at)`, `final=1` reads, both
  full-text index layers on messages.
- Parse-on-client; the shipper still runs the 17 adapters and writes typed rows.
- `sessions_v` as a **saved query** run under the caller, not a stored view.
- The REST contract and the borrowed dashboard.

## Measured facts (ClickHouse 26.7.1, disposable lab)

Carried from v1, still load-bearing. Re-run before building; do not take on trust.

1. Prefix-wildcard grants exist and enforce, **but collide across handles** — hence
   explicit grants. Suffix wildcards are a syntax error.
2. Members can self-provision inside their own prefix and are **denied outside it**.
3. `Merge` **fails closed on permissions** — a caller granted the Merge room plus one
   underlying room sees only that room's rows.
4. `Merge` **auto-discovers** rooms created after it exists.
5. `Merge` **tolerates schema drift**, returning a column's default for rooms that lack
   it — which is what makes schema rollout progressive.
6. Row-policy rights are **house-scopeable**: `GRANT ACCESS MANAGEMENT ON mem.*`
   expands to `CREATE/ALTER/DROP/SHOW ROW POLICY ON mem.*`. Owner only — the scope is
   the house, not a room, so any holder could attach policies to another member's rooms.

### New in v2 — ClickHouse has no impersonation

Tested, because v1's migration section assumed one might exist:

- `SET SESSION AUTHORIZATION` — does not exist (syntax error).
- `SET ROLE` — leaves `currentUser()` unchanged; roles carry privileges, not identity.

So there is no way for one credential to write rows stamped as another member. The only
way to produce a row with `user_id = 'alice'` is to authenticate as alice. This does not
block anything in v2 — it is recorded so migration is not planned around a mechanism
that isn't there.

## Phases

1. **Schema + naming** — room DDL template, key order, the Merge rooms, handle validation.
2. **Provisioning** — kernel capability and standalone path; the exact grant set.
3. **Query layer** — `sessions_v` as a saved query; how the shipper, server, and skills
   resolve the caller's room names.
4. **Sharing** — room-level self-serve grants; row-level partial sharing via the owner.

Migration is **not** a phase here. See `MIGRATION-v2-2026-08-02-22_42.md`.

## Open questions

- **Handle validation.** Forbid `_` in handles? With suffix naming and explicit grants
  the collision risk is gone, but `messages_alice_bob` is still ambiguous to a human
  and to any future splitter.
- **Key order.** With one room per member, does `user_id` still earn a slot in
  `ORDER BY`, or is `(session_id, seq)` enough?
- **May members create and drop their own rooms?** The lab says they can, safely
  scoped. Against: a member can then drop their own memory, and schema rollout stops
  being centrally enforceable.
- **Standalone path.** Without a kernel there is no capability layer, and a standalone
  user is both owner and member. One credential with both roles, or two?
- **Merge room ownership** — owner creates and migrates them, presumably in the same
  capability that provisions member rooms.

## Out of scope

- **Migration** from the current shared-room house. Separate task.
- **`agent_id` / crew identity.** Deferred. Standing note: within a crew sharing one
  credential, any agent tag is client-supplied and therefore not a security boundary;
  enforced separation needs separate users, which is this design one level down.
- Adapters, REST contract, dashboard.
