# per-member rooms — plan v3 (2026-08-02-22_49)

Supersedes `PLAN-v2-2026-08-02-22_42.md`. v1 and v2 are kept as written.

**v3 exists to correct one wrong claim in v2.** Everything else — house `mem`, type-first
room naming, deferred migration — is unchanged.

## Correction: ClickHouse *does* have impersonation

v2 stated flatly that ClickHouse has no impersonation. That was wrong, and the way it was
wrong is worth recording: two negative tests (`SET SESSION AUTHORIZATION`, `SET ROLE`)
were treated as proof of absence, instead of looking for the feature that does exist.

`EXECUTE AS` exists and changes `currentUser()`. Measured on 26.7.1:

```sql
EXECUTE AS zed SELECT currentUser()   -- → zed
```

It is a **grantable privilege, denied by default**:

- a plain member attempting `EXECUTE AS ben …` gets `Not enough privileges`;
- after `GRANT EXECUTE AS ON *.* TO amy`, the same statement returns `ben`.

## What that changes

**The provenance property is narrower than v2 claimed.** v2 said a `user_id` stamp is
"proof rather than convention". Correctly stated:

> `user_id` is unforgeable **by a member**, because members are not granted `EXECUTE AS`.
> It is forgeable by anyone who holds that grant — the owner, or anyone the owner grants
> it to.

That is still a useful guarantee and it is the normal one: the owner is already trusted
with everything inside its own house. But the trust boundary is the owner, not the
engine. Do not grant `EXECUTE AS` to members.

**Migration is unblocked.** v1 and v2 treated per-member provenance as the hard problem
in any fan-out, since `user_id` is `MATERIALIZED currentUser()` and cannot be inserted.
`EXECUTE AS` resolves it directly — the owner writes each member's rows under that
member's identity without holding their credential.

Migration stays deferred, and it should not shape MVP decisions. It is recorded as
solved-in-principle so nobody re-derives it as a blocker.

## Unchanged from v2

- House is **`mem`**; rooms are `sessions_<m>`, `messages_<m>`, `tool_calls_<m>`.
- Merge rooms anchor on the room type — `Merge('mem', '^messages_')` — which cannot
  match `all_messages`.
- Three explicit grants per member, `WITH GRANT OPTION`. No wildcards in either
  direction: `mem.alice_*` also matches `alice_bob_*`, and `mem.*_alice` is a syntax
  error.
- `user_id MATERIALIZED currentUser()` on every room, `async_insert=0` on writers.
- `sessions_v` is a saved query run under the caller, not a stored view.
- Parse-on-client, typed rooms, `extra JSON`, `ReplacingMergeTree(ingested_at)`,
  `final=1` reads, both full-text layers on messages.

## Measured facts (ClickHouse 26.7.1)

1. Prefix-wildcard grants enforce but **collide across handles** — explicit grants only.
   Suffix wildcards are a syntax error.
2. Members **self-provision** inside their own prefix and are denied outside it.
3. `Merge` **fails closed on permissions** — a caller sees only the underlying rooms they
   hold grants for.
4. `Merge` **auto-discovers** rooms created after it.
5. `Merge` **tolerates schema drift**, returning defaults for rooms lacking a column, so
   schema rollout is progressive rather than lock-step. It **rejects mutations** —
   use `ADD COLUMN`, Merge room first.
6. Row-policy rights are **house-scopeable** (`GRANT ACCESS MANAGEMENT ON mem.*`). Owner
   only — the scope is the house, not a room.
7. **`EXECUTE AS` exists, changes `currentUser()`, and is denied to members by default.**

## Phases

1. Schema + naming — room DDL template, key order, Merge rooms, handle validation.
2. Provisioning — kernel capability and standalone path; the grant set.
3. Query layer — `sessions_v` as a saved query; resolving the caller's room names.
4. Sharing — room-level self-serve; row-level via the owner.

Migration is not a phase. Do not let it block MVP.

## Open questions

- **May members create and drop their own rooms?** Works, safely scoped; but a member
  could drop their own memory and schema rollout stops being central.
- **Key order** — is `user_id` still worth an `ORDER BY` slot now the room is the tenant?
- **Standalone path** — a user with no kernel is both owner and member; one credential or
  two?
- **Is `EXECUTE AS` scopeable?** It was granted `ON *.*` in the lab. If it can be scoped
  to `mem.*`, an owner could hold it for its own house only — worth testing before any
  migration work.
- **Handle validation** — forbid `_`? No longer a security question under type-first
  naming, but `messages_alice_bob` is still ambiguous to a reader.

## Out of scope

- Migration (deferred; unblocked in principle, see above).
- `agent_id` / crew identity. Standing note: within a crew sharing one credential, an
  agent tag is client-supplied and is not a security boundary.
- Adapters, REST contract, dashboard.
